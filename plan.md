# План демо: мини-платформа проценки

## Цель и границы

Показать законченный цикл: сбор цен конкурентов → безопасный расчёт цены → объяснение результата менеджеру → выдача опубликованных цен через JSON API без Excel.

Два равных акцента:

- **Парсинг и его поломки.** Парсеры регулярно ломаются, когда площадка меняет вёрстку или защиту. Демо показывает, что каждая поломка замечается, получает точную причину и не превращается в цену.
- **Деньги и публикация.** Ошибка в коде — неверная цена у клиента. Демо показывает наценку, округление, карантин и объяснение «почему цена такая».

Это локальное демо для одного пользователя: 20–30 подготовленных товаров, два источника, один воркер. Ядро рассчитано на 3 сосредоточенных дня при знакомом стеке; это оценка, а не обещание срока. Расширения добавляются только после готовности ядра, в указанном порядке.

## Стек

- Python 3.13, uv, ruff, mypy.
- FastAPI, Pydantic v2.
- SQLAlchemy 2 async, asyncpg, PostgreSQL 16, Alembic.
- httpx.AsyncClient для запросов и сессий, selectolax для HTML, tenacity для повторов.
- Decimal в Python, NUMERIC(12,2) в БД; в JSON деньги передаются строками.
- React, TypeScript, Vite, TanStack Query. Одна таблица и раскрываемые детали, без графиков.
- Docker Compose: api, worker, postgres, fake-sites, nginx (статика фронтенда и проксирование API).
- pytest, включая интеграционные тесты на PostgreSQL.
- structlog: JSON-логи с run_id, source и product_id; endpoint /health.

Не строим универсальный движок правил, систему плагинов и очередь задач общего назначения.

## Данные

Подготовленный набор содержит бренд, артикул, закупку, текущую опубликованную цену и настройки расчёта. Все цены в рублях за одну штуку, на одинаковой налоговой основе.

Нормализация артикулов и брендов — часть показа, а не скрытая деталь:

- артикул очищается от пробелов и разделителей: `0 986-452 041` → `0986452041`, `OC 90` → `OC90`;
- синонимы брендов сводятся к одному: `MB` = `Mercedes-Benz`, `MANN` = `MANN-FILTER`;
- исходные значения сохраняются рядом с нормализованными;
- в наборе есть предложение с тем же артикулом, но другим брендом: оно отбрасывается с причиной «другой бренд».

Таблица синонимов задана только для демонстрационного набора.

## Источники и парсеры

Один сервис fake-sites предоставляет два независимых источника. В README явно указано, что они синтетические.

| Источник | Что показывает |
|---|---|
| HTML-каталог | разбор вёрстки: артикул, бренд, цена, остаток, срок поставки |
| Скрытый JSON API | страница грузит цены через XHR; парсер получает сессионную cookie и ходит прямо в API в той же сессии |

Режимы переключаются HTTP-запросом без перезапуска; в UI есть селектор режима для каждого источника.

| Режим | Поведение площадки | Что делает парсер |
|---|---|---|
| normal | корректные данные | возвращает предложения |
| markup_changed | другая разметка, обязательных полей нет | ошибка «изменилась структура», без повторов |
| unavailable | таймаут или 503 | ограниченные повторы с паузой, затем ошибка «недоступен» |
| blocked | 403 со страницей капчи или 429 | ошибка «заблокирован»; 429 повторяется с учётом Retry-After в пределах бюджета времени, 403 не повторяется |
| price_spike | цена контрольного товара падает с 2 000 до 1 500 ₽ | данные корректны; срабатывает карантин |

Контрольный товар для price_spike: закупка 1 000 ₽, нижняя граница 1 200 ₽, опубликованная цена 1 990 ₽, порог изменения 20 %. Новая рекомендация 1 490 ₽, изменение −25,1 % → карантин. Числа подобраны так, чтобы результат не упирался в нижнюю границу и не попадал под фильтр подозрительно низкой цены: при опубликованной цене рядом с нижней границей падение конкурента карантина не даёт.

Правила для парсеров:

- общий интерфейс: источник возвращает либо список предложений, либо ошибку одного из трёх типов — сеть, структура, блокировка;
- отсутствие обязательного поля или цена, которую не удалось разобрать, — ошибка структуры, а не цена 0 и не «товара нет»;
- сбор идёт параллельно с ограничением числа одновременных запросов и таймаутами;
- у каждого источника есть бюджет времени на весь сбор, включая паузы между повторами (в демо 30 секунд). Если Retry-After не помещается в остаток бюджета, источник сразу завершается ошибкой «заблокирован»;
- прокси — настройка источника, передаётся в httpx.AsyncClient; пула и ротации в ядре нет;
- во время HTTP-запросов транзакция БД не открыта.

`docs/runbook.md` — одна страница: как по статусу прогона и логам понять, какой из трёх типов ошибки произошёл, и что делать в каждом случае.

## Правила расчёта

Правила фиксированы и описаны в `docs/pricing.md`; редактора настроек нет.

1. Принимаем предложения нужного товара (после нормализации бренда и артикула) с положительной ценой, наличием и допустимым сроком поставки.
2. Предложение с ценой ниже закупка × 0,5 отбрасывается с причиной «подозрительно низкая цена». Это защита от мусора вроде «1 250» → 1; коэффициент — настройка.
3. Достаточно одного пригодного предложения. Если один источник упал, расчёт по второму допускается, результат помечается «по частичным данным».
4. Целевая цена = минимальная пригодная цена конкурента − фиксированный шаг.
5. Нижняя граница = закупка × (1 + минимальная **наценка**). Это наценка на закупку, не маржа от выручки. Цена ниже нижней границы не публикуется никогда.
6. Если задан потолок, ограничиваем результат сверху. Если потолок ниже нижней границы — конфликт правил, новую цену не публикуем.
7. Нижняя граница округляется вверх до копейки, потолок — вниз. Целевая цена округляется до копейки по ROUND_HALF_UP, затем ограничивается интервалом.
8. Изменение относительно опубликованной цены: abs(new − old) / old × 100. Больше порога — рекомендация уходит в карантин. Если опубликованной цены ещё нет, первая рекомендация тоже уходит в карантин.
9. Нет пригодных предложений, некорректная закупка или конфликт правил — новую цену не публикуем, предыдущая остаётся, UI показывает причину и дату её расчёта.

Состояние результата по товару: опубликована, без изменений, карантин, оставлена предыдущая (с причиной).

Для каждого расчёта сохраняем: закупку и настройки на момент расчёта, версию правил, учтённые и отброшенные предложения с причинами, целевую цену, границы, итог и решение.

Контрольный пример: закупка 1 000 ₽, наценка 20 %, конкурент 1 250 ₽, шаг 10 ₽ → 1 240 ₽. При конкуренте 1 100 ₽ результат ограничивается снизу: 1 200 ₽.

**Известное ограничение ядра.** Подтверждения карантина нет, поэтому рекомендация из карантина сама не публикуется: если рынок действительно сдвинулся, цена останется прежней до расширения 1. Это описано в README.

## Прогоны и устойчивость

- Прогон создаётся ручным запросом к API или тем же воркером по фиксированному интервалу. Отдельного сервиса-планировщика нет.
- Одновременно существует один ожидающий или активный прогон; это обеспечивает частичный уникальный индекс в БД. Повторный запрос запуска возвращает идентификатор уже существующего прогона.
- Воркер забирает прогон запросом с `FOR UPDATE SKIP LOCKED`. Поддержка нескольких воркеров не заявляется и не проверяется.
- Статусы прогона: queued, running, succeeded, partial, failed. Карантин — состояние товара, а не ошибка прогона.
- При старте воркер переводит оставшийся running в failed с причиной interrupted. Следующий прогон начинается заново.
- Результаты сбора и расчёта сохраняются первыми; затем одна короткая транзакция публикует допустимые цены и завершает прогон. Уникальное ограничение (run_id, product_id) исключает дубли.
- Сбой одного источника — partial. Сбой обоих — failed, опубликованные цены не меняются. Успешный сбор без пригодных предложений показывается отдельно от технического сбоя.
- Предложения прошлых прогонов в новый расчёт не попадают; история хранится для объяснения прежних решений.

## UI и обмен без Excel

Один экран:

- кнопка запуска, статус последнего прогона, состояние каждого источника с типом ошибки;
- селектор режима для каждого источника (панель «Демо»);
- таблица товаров: закупка, опубликованная цена, новая рекомендация, состояние, время расчёта;
- раскрытие «Почему цена такая»: предложения, причины исключения, формула с подставленными числами, сработавшие ограничения.

`GET /api/published-prices` выдаёт только опубликованные цены, их даты и идентификаторы расчётов; рекомендации из карантина в выдачу не входят. Это минимальный контракт для системы прайс-листов; принимающую систему не строим.

Предложения пишутся в БД пакетной вставкой, опубликованные цены — через `ON CONFLICT`. Проверки на больших объёмах нет, и в README это сказано прямо.

## Сверка

В ядре сверка — это файл `control_cases.csv`: в каждой строке входные данные расчёта (закупка, наценка, шаг, потолок, предложения) и вручную рассчитанный ожидаемый результат. Параметризованный тест прогоняет все строки через функцию расчёта и показывает число совпадений и расхождений.

Входные данные лежат рядом с ожидаемым результатом, поэтому любое расхождение можно разобрать. Это контрольные примеры, а не доказательство совместимости со старой системой; заранее обещанных процентов нет.

Отдельная команда сверки с выгрузкой из старой системы — расширение 3.

## Тесты

- контрольные примеры из `control_cases.csv`, наценка и округление у границ;
- режим price_spike на контрольном товаре проходит весь путь от источника до карантина;
- Retry-After больше бюджета времени сразу даёт ошибку блокировки, без ожидания;
- потолок ниже нижней границы; нулевая и некорректная закупка;
- пустой список предложений, другой бренд, подозрительно низкая цена;
- нормализация артикулов и синонимы брендов;
- скачок цены и отсутствие предыдущей цены дают карантин;
- сломанная разметка даёт ошибку структуры, а не цену 0;
- 403 и 429 дают ошибку блокировки, 503 — ошибку сети; повторы только там, где они заданы;
- один источник упал — второй обработан, прогон partial;
- оба источника упали — опубликованные цены не изменились;
- второй запрос запуска возвращает тот же прогон;
- перезапуск воркера не оставляет прогон в running;
- JSON API не выдаёт рекомендации из карантина.

## Порядок реализации

| День | Результат |
|---|---|
| 1 | Compose, схема и миграция, seed. Один товар проходит весь путь: сбор с HTML-источника → расчёт → запись → простая страница. Денежный расчёт и его тесты |
| 2 | Второй источник с сессией, режимы сбоев и три типа ошибок, нормализация, воркер с расписанием, partial, карантин, публикация |
| 3 | Экран с объяснением цены и панелью режимов, JSON API. Запуск на чистом окружении, прогон всего сценария и тестов, исправления. После этого README, runbook и видео |

При нехватке времени убираем оформление и расширения, но сохраняем проверки денег, типы ошибок парсеров и публикацию.

## Расширения — по порядку

1. **Подтверждение карантина.** Кнопка «Подтвердить» публикует рекомендацию. Подтвердить можно только рекомендацию последнего завершённого прогона и не старше заданного возраста: более новый прогон отменяет старые рекомендации. Перед записью в той же транзакции проверяется это условие, а также то, что закупка и версия правил не изменились с момента расчёта; иначе требуется новый расчёт.
2. **Selenium.** Третий источник, цены которого подгружает JS; один браузерный парсер через контейнер `selenium/standalone-chrome`.
3. **Команда сверки.** `compare --run-id … file.csv` принимает CSV «бренд, артикул, ожидаемая цена» и сравнивает его с рекомендациями выбранного прогона. Для каждой строки выводит ожидаемое значение, фактическое, разницу и объяснение нового расчёта. Причину расхождения со старой системой команда не называет: для этого нужны входные данные старого расчёта.
4. **CI.** GitHub Actions: lint, mypy, тесты на PostgreSQL в service container.
5. **VPS.** Развёртывание одной командой; управляющие endpoints и панель режимов закрыты от публичного доступа.

## Сценарий показа — 5 минут

1. `docker compose up --build`; миграции и seed выполняются автоматически.
2. Ручной прогон: итог 1 240 ₽, раскрыть расчёт. Показать отброшенные предложения: другой бренд и подозрительно низкая цена.
3. Режим markup_changed у HTML-источника: ошибка «изменилась структура», прогон partial, цены посчитаны по второму источнику.
4. Режим blocked: та же картина, но причина другая — «заблокирован». Открыть runbook.
5. Режим price_spike: контрольный товар в карантине с рекомендацией 1 490 ₽ (−25,1 %), опубликованная цена прежняя — 1 990 ₽.
6. Открыть JSON API: рекомендации из карантина в выдаче нет.
7. Запустить тест контрольных примеров и показать число совпадений.

Чтобы шаги не ломали друг друга, seed подчиняется трём условиям:

- у товара из шага 2 исходная опубликованная цена 1 260 ₽, поэтому первый прогон публикует 1 240 ₽, а не показывает «без изменений»;
- режимы markup_changed и blocked включаются на HTML-источнике, price_spike — на JSON-источнике; перед шагом 5 HTML-источник возвращается в normal;
- минимальное предложение контрольного товара price_spike лежит в JSON-источнике, поэтому сбои HTML-источника в шагах 3–4 не меняют его опубликованную цену 1 990 ₽.

Команда сброса возвращает демо в исходное состояние, после неё каждый шаг воспроизводится. Расписание и восстановление после остановки воркера показываются отдельно.

## Что сознательно отложено

- Пул прокси с ротацией, решатель капчи, circuit breaker.
- Отсечение выбросов по медиане и IQR: при двух источниках не имеет смысла.
- TTL предложений: в прогон попадают только свежесобранные данные.
- IMAP/SMTP, Excel, загрузка файлов, рассылки и клиентские прайс-листы.
- Графики, дашборд, редактор правил.
- Постраничная выдача в JSON API: для 30 товаров не нужна.
- Несколько воркеров и распределённый планировщик.
- Вымышленный legacy-движок, Hypothesis, ADR.

## Критерий готовности

На чистом окружении демо запускается по README и проходит весь сценарий без ручной правки БД. Каждая цена объяснена, каждая ошибка источника имеет тип. Некорректные рекомендации и рекомендации из карантина не публикуются. В документации названы синтетические источники, один воркер, отсутствие подтверждения карантина и отсутствие проверки на больших объёмах.
