# Воркфлоу реализации

Как строится демо из `plan.md`: прораб режет работу на законченные шаги и запускает каждый шаг в отдельном bb-треде, строго последовательно. Один шаг — один коммит в `main`. Пользователь в процессе не участвует.

## Роли

| Роль | Кто | Что делает |
|---|---|---|
| Прораб | тред-оркестратор (Claude Code) | пишет задание шага, запускает тред шага, принимает отчёт, запускает следующий шаг. Сам код не пишет и проверки не запускает |
| Исполнитель | тред шага (Claude Code, Opus 5.5), дочерний к прорабу | реализует шаг, сам гоняет проверки, сам вызывает ревью, исправляет замечания, коммитит |
| Ревьюер | тред ревью (Codex, `gpt-6-astra`), дочерний к исполнителю | независимо читает изменения шага и возвращает замечания. Файлы не меняет |

Все треды работают в одном окружении — checkout проекта (`env_hax3d45zke`). Шаги идут последовательно, поэтому конфликтов нет и worktree не нужны.

## Цикл шага

### Прораб

1. Пишет задание по шаблону ниже.
2. Запускает тред шага:
   ```sh
   bb thread spawn --project proj_x4dtacwx9q --parent-self \
     --environment env_hax3d45zke --provider claude-code \
     --title "Шаг N: <название>" --prompt-file <задание>
   ```
3. Ждёт уведомления о завершении треда. Отчёт исполнителя — его финальный ответ.
4. Принимает шаг, если в отчёте есть всё из раздела «Отчёт исполнителя», коммит шага виден в `git log`, а `docs/progress.md` обновлён. Проверки прораб не перезапускает.
5. Если отчёт неполный, проверки красные или ревью не закрыто — пишет замечания в тот же тред (`bb thread tell`), а не создаёт новый.
6. Запускает следующий шаг.

Развилки, не описанные в `plan.md`, прораб решает сам и записывает решение в задание следующего шага. Останавливается и пишет пользователю только при блокере, который нельзя обойти: не работает Docker, нужен доступ или секрет, противоречие в `plan.md`, которое меняет смысл демо.

### Исполнитель

1. Читает `AGENTS.md`, `plan.md`, `docs/progress.md` и задание.
2. Реализует шаг вместе с тестами.
3. Гоняет все проверки из `AGENTS.md`, пока они не станут зелёными.
4. Индексирует изменения: `git add -A`.
5. Вызывает ревью (см. ниже) и ждёт результат.
6. Исправляет замечания, с которыми согласен; несогласие обосновывает в отчёте. После исправлений снова гоняет проверки и `git add -A`. Если были замечания уровня «блокер» или «серьёзное», вызывает повторное ревью. Всего не больше трёх раундов ревью; оставшееся выносит в отчёт.
7. Дописывает `docs/progress.md` и делает один коммит шага.
8. Возвращает отчёт финальным ответом.

### Ревью

Исполнитель запускает ревьюера и ждёт его в том же ходе:

```sh
bb thread spawn --project "$BB_PROJECT_ID" --parent-self --parent-notifications off \
  --environment "$BB_ENVIRONMENT_ID" --provider codex --model gpt-6-astra \
  --title "Ревью шага N" --prompt-file <промпт ревью>
bb thread wait <id ревьюера> --timeout 40m
bb thread output <id ревьюера>
```

Если `wait` вышел по таймауту, исполнитель смотрит `bb thread show <id>`: ревьюер может ждать подтверждения. Повторное ревью — сообщение тому же ревьюеру через `bb thread tell`, затем снова `wait` и `output`.

Промпт ревью:

```
Ты независимый ревьюер шага N демо из plan.md. Файлы не меняй и не коммить.

Изменения шага проиндексированы: смотри `git diff --cached` (на первом шаге — все файлы в индексе).
Задание шага: <вставить задание>.
Правила проекта: AGENTS.md. Спецификация: plan.md.

Ищи в первую очередь:
- ошибки в деньгах: Decimal, округление, границы, наценка, карантин, публикация;
- расхождения с plan.md и заданием шага;
- ошибки парсеров, превращающиеся в цену или «товара нет»;
- транзакции, гонки, повторы, таймауты;
- тесты, которые ничего не проверяют, или непроверенные требования шага.

Стиль и вкусовщину не пиши. Для каждого замечания: уровень (блокер / серьёзное / мелкое),
файл и строка, что не так, сценарий, при котором это ломается.
В конце — вердикт: «принять» или «доработать».
```

## Задание шага — шаблон

```
Шаг N из workflow.md: <название>.

Цель: <одно-два предложения>.
Разделы plan.md: <список>.
Уже сделано: <кратко; детали в docs/progress.md>.
Решения прораба для этого шага: <если есть>.
Не входит в шаг: <что не делать>.
Готово, когда: <критерий из таблицы шагов + конкретные тесты>.

Работай по циклу исполнителя из workflow.md: проверки, ревью codex gpt-6-astra, один коммит.
```

## Отчёт исполнителя

- хеш и сообщение коммита;
- что сделано, по пунктам;
- проверки: какие команды запускались и с каким итогом (число тестов);
- ревью: id треда ревьюера, число раундов, итоговый вердикт, что исправлено, что отклонено и почему;
- отступления от `plan.md` и открытые вопросы для следующих шагов.

## Сбой шага

Если шаг не удаётся довести до зелёных проверок за разумное время, исполнитель не коммитит полуготовое, а возвращает отчёт с причиной. Прораб либо уточняет задание в том же треде, либо делит шаг на два.
