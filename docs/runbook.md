# Runbook: парсер сломался

Как по статусу прогона, экрану и логам понять, какой из трёх типов ошибки источника произошёл, и что делать. Запуск демо — [README](../README.md), правила расчёта — [pricing.md](pricing.md), требования — [plan.md](../plan.md#источники-и-парсеры).

Каждый источник в прогоне заканчивается либо списком предложений, либо ошибкой ровно одного типа. Ошибка на любом артикуле делает весь источник failed в этом прогоне: его предложения не пишутся и в расчёт не идут. Ошибка парсинга никогда не становится ценой 0 или «товара нет».

| Тип (`error_kind`) | Подпись на экране | Повторы |
|---|---|---|
| `structure` | изменилась структура | нет |
| `network` | недоступен | да: 3 попытки всего, пауза 1 с, в пределах бюджета |
| `blocked` | заблокирован | 403 — нет; 429 — до 2 повторов после `Retry-After`, если пауза помещается в бюджет |

Бюджет — 30 с на весь сбор источника, включая паузы между повторами; после его исчерпания новый запрос не отправляется и пауза не начинается. Таймаут httpx — 5 с (не больше остатка бюджета) на каждую сетевую операцию запроса (соединение, ожидание и чтение очередной порции ответа), а не на запрос целиком: ответ, приходящий частыми мелкими порциями, может читаться дольше 5 с, но весь запрос обрывается по концу бюджета (это ожидаемое поведение, тест `test_slow_trickling_response_is_cut_at_the_end_of_the_budget`).

## Где смотреть

Команды ниже — для POSIX-оболочки (на Windows — Git Bash); варианты для PowerShell приведены рядом.

**Экран** (http://127.0.0.1:8080): блок «Источники — прогон №N» показывает последний завершённый прогон: у каждого источника «ok» или «ошибка: <подпись>», сообщение, число предложений. Статус прогона — в шапке. Товары, посчитанные по одному источнику, помечены «по частичным данным».

**API**: `GET /api/status` — `last_finished_run` (и `latest_run`, `active_run`), `GET /api/runs/{id}` — конкретный прогон:

```sh
curl http://127.0.0.1:8080/api/status
```

```json
  "finish_reason_label": "все источники завершились ошибкой",
  "sources": [
    {
      "source": "html_catalog",

      "error_kind": "network",
      "error_label": "недоступен",
```

(ответ сокращён). `status: "ok"` с `offer_count: 0` — источник ответил, но предложений нет: это не сбой, а «нет пригодных предложений» у товаров.

<a id="логи"></a>**Логи** — одна JSON-строка на запись: `timestamp`, `level`, `logger`, `event`, `service` и контекст. У воркера в каждой строке `run_id` (`null` вне прогона); строки сбора источника — с `source`, строки расчёта товара — с `product_id`.

```sh
docker compose logs worker --no-log-prefix | grep '"event": "source failed"'     # все ошибки источников с типом и сообщением
docker compose logs worker --no-log-prefix | grep '"run_id": 3,'                  # всё про прогон 3
docker compose logs worker --no-log-prefix | grep '"run_id": 3,' | grep '"source": "html_catalog"'
docker compose logs worker --no-log-prefix | grep -E 'network failure, retrying|rate limited'   # повторы
```

В PowerShell вместо `grep` — `Select-String` (`-SimpleMatch` — искать строку буквально):

```powershell
docker compose logs worker --no-log-prefix | Select-String '"event": "source failed"' -SimpleMatch
docker compose logs worker --no-log-prefix | Select-String '"run_id": 3,' -SimpleMatch
(Invoke-RestMethod http://127.0.0.1:8080/api/status).last_finished_run.sources | Select-Object source, status, error_kind, error_message
```

```json
{"failure": "HTTP 503", "path": "/html/search", "attempt": 1, "pause_seconds": 1.0, "event": "network failure, retrying", "run_id": 2, "source": "html_catalog", "level": "warning", "logger": "app.parsers", "timestamp": "2026-11-12T04:40:03.188867Z", "service": "worker"}
{"status": "partial", "calculations": 25, "published": 0, "event": "run finished", "run_id": 2, "level": "info", "logger": "app.worker", "timestamp": "2026-11-12T04:39:48.726568Z", "service": "worker"}
```

Сброс демо начинает нумерацию прогонов заново, поэтому в логах за день может быть несколько прогонов с одним `run_id`: сверяйте `timestamp` или добавьте `--since 10m`. Логи живут в контейнере: `docker compose restart worker` их сохраняет, а пересоздание (`docker compose up -d worker` с другими переменными, `docker compose down`) — нет. Другие события прогона: `run started`, `source collection started`, `source collected`, `price calculated`, `run finished`.

## Структура (`structure`) — «изменилась структура»

Признаки: площадка ответила, но не так, как ожидает парсер — нет блока результатов или обязательного поля, цена не разбирается, другая схема JSON, неожиданный HTTP-код (404, редирект), нет сессионной cookie. Ошибка возникает с первого запроса, повторов в логе нет.

Примеры сообщений:

- `на странице поиска нет блока результатов (#offers) (артикул 06J115403Q)` — HTML, режим `markup_changed`;
- `в ответе API нет обязательного поля «offers» (артикул 0242236562)` — JSON, режим `markup_changed`;
- `нет обязательного поля «цена»` (HTML), `нет обязательного поля «цена» (price)` (JSON), `не удалось разобрать поле «цена»: '…'`, `больше двух знаков после запятой в поле «цена»: '…'`, `отрицательное значение в поле «остаток»: …`;
- `неожиданный ответ площадки: HTTP 404 на /html/search (артикул …)`;
- `страница /json/ не выдала сессионную cookie «session»`.

Что делать: **чинить парсер** — повторы не помогут, площадка изменилась. Сохранить ответ площадки, сравнить с тем, что ждёт парсер (`backend/app/parsers/html_catalog.py`, `backend/app/parsers/json_api.py`, разбор полей — `backend/app/parsers/fields.py`), поправить разбор и добавить фикстуру с новой разметкой в тесты (`backend/tests/data/html/`, `backend/tests/unit/parsers/`). Пока парсер не починен, цены считаются по второму источнику с пометкой «по частичным данным».

## Сеть (`network`) — «недоступен»

Признаки: таймаут, ошибка соединения или прокси, HTTP 5xx. В логе перед ошибкой — строки `network failure, retrying` с `attempt` и `pause_seconds`.

Примеры сообщений:

- `площадка недоступна: HTTP 503 на /html/search (артикул 0986452041), попыток: 3` — режим `unavailable`;
- `площадка недоступна: таймаут запроса на …, попыток: 3`, `площадка недоступна: ошибка соединения ConnectError на …, попыток: 3`;
- `площадка недоступна: … ; бюджет времени 30 сек. исчерпан` — повторы съели бюджет.

Что делать: **повторы уже были** (3 попытки с паузой), повторять вручную сразу бессмысленно. Проверить доступность площадки и прокси (`curl` с той же машины, `docker compose ps fake-sites`), подождать и запустить следующий прогон или дождаться расписания. Код не трогать, пока площадка не ответит иначе.

## Блокировка (`blocked`) — «заблокирован»

Признаки: 403 (страница капчи), 429 (слишком много запросов), повторный 401 у JSON API после переоткрытия сессии.

Примеры сообщений:

- `доступ запрещён (страница капчи): HTTP 403 на /html/search (артикул 0986452041)` — HTML, режим `blocked`; **403 не повторяется**, ошибка после первого же запроса;
- `слишком много запросов: HTTP 429 на /json/ (страница сессии), Retry-After 60 сек. не помещается в остаток бюджета 30.0 сек. из 30 сек.` — JSON, режим `blocked`: пауза больше остатка бюджета, источник завершается сразу, **без ожидания**;
- `слишком много запросов: HTTP 429 на …, повторов после Retry-After: 2` — 429 повторялся, пока не кончились разрешённые повторы;
- `доступ отклонён: HTTP 401 на /json/api/offers (артикул …) после переоткрытия сессии`.

429 с `Retry-After`, который строго меньше остатка бюджета, повторяется после паузы (в логе — `rate limited (HTTP 429), retrying after a pause` с `retry_after`); если площадка успела «остыть», источник заканчивается успешно.

Что делать: снизить нагрузку на площадку (`SOURCE_CONCURRENCY`, реже прогоны) и подождать — повторы при 403 бессмысленны. Если площадка блокирует по адресу, поможет **прокси — это настройка источника**: `HTML_CATALOG_PROXY` / `JSON_API_PROXY` (URL, передаётся в `httpx.AsyncClient` этого источника). В compose эти переменные сервису worker не передаются: их нужно добавить в `environment` сервиса `worker` в `deploy/compose.yaml`. Пула прокси, ротации и решателя капчи в ядре нет (сознательно отложено).

## Что прогон означает для цен

| Статус прогона | Когда | Цены |
|---|---|---|
| `succeeded` | оба источника ok | расчёт по обоим; публикуются только «опубликована» |
| `partial` | один источник упал | расчёт по второму, «по частичным данным»; публикация по тем же правилам, включая карантин |
| `failed` / `all_sources_failed` | оба источника упали | расчётов нет, **опубликованные цены не меняются** |
| `failed` / `interrupted` | воркер остановился во время прогона (отмечается при его следующем старте) | ничего не опубликовано; следующий прогон начинается заново |
| `failed` / `internal_error` | исключение в коде воркера (в логе — поле `exception` с трассировкой и `run_id`) | ничего не опубликовано; это баг, а не сбой источника |

Ни один тип ошибки источника не превращается в цену: при поломке опубликованная цена либо остаётся прежней, либо считается только по исправному источнику.

## Вернуть режим и сбросить демо

```sh
curl http://127.0.0.1:8080/api/demo/modes                                    # текущие режимы
curl -X PUT http://127.0.0.1:8080/api/demo/modes/html_catalog -H 'content-type: application/json' -d '{"mode":"normal"}'
curl -X PUT http://127.0.0.1:8080/api/demo/modes/json_api -H 'content-type: application/json' -d '{"mode":"normal"}'
curl -X POST http://127.0.0.1:8080/api/demo/reset                            # БД в состояние seed, оба источника в normal
```

На экране — селекторы в панели «Демо» и кнопка «Сбросить демо». Сброс отвечает 409, пока прогон в очереди или выполняется (например, ждёт `Retry-After`): подождите завершения и повторите. Режимы живут в памяти fake-sites: `docker compose restart fake-sites` тоже возвращает оба источника в `normal`.
