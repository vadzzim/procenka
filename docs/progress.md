### Решения

- uv-проект не в корне, а в `backend/`; команды из корня вызываются как `uv run --directory backend ...`, чтобы конфигурация ruff/mypy/pytest бралась из `backend/pyproject.toml`.

- Учётные данные postgres по умолчанию (`procenka/procenka`) — только для локального демо; порт опубликован только на `127.0.0.1`.

## Шаг 2. Ядро расчёта и нормализация

### Что сделано

- `backend/app/pricing/` — чистые функции без БД, сети, времени и окружения:
  - `money.py` — `money()` (Decimal/int/str → Decimal без округления), `require_decimal()` и округление `ceil_cents` / `floor_cents` / `half_up_cents` / `half_up_tenth`. `float`, `bool` и прочие типы → `TypeError`, NaN и бесконечности → `ValueError`;
  - `normalize.py` — `normalize_article()`, `normalize_brand()` и таблица синонимов демо-набора `BRAND_SYNONYMS`;
  - `models.py` — входные dataclass-ы `Product`, `ProductSettings`, `GlobalSettings`, `Offer`; результат `PricingResult`; enum-ы `OfferRejection`, `ResultState`, `ResultReason`, `Constraint` с английскими кодами и одна таблица русских подписей `LABELS`; константа `RULES_VERSION`;
  - `calculate.py` — `calculate_price(product, settings, offers, *, global_settings, partial_data)`.
- `backend/tests/data/control_cases.csv` — 25 вручную рассчитанных примеров, формат описан в `backend/tests/data/README.md`. Параметризованный тест `tests/unit/pricing/test_control_cases.py`; `tests/conftest.py` печатает `control cases: N matched, M mismatched`, расхождение показывает входные данные строки, ожидаемое, фактическое и промежуточные числа.
- Unit-тесты: `test_money.py` (округление у границ, отказ от float и нефинитных значений во всех входных dataclass-ах и функциях округления), `test_normalize.py` (примеры из `plan.md`, синонимы, неизвестный бренд), `test_calculate.py` (каждое правило и граница, порядок причин отбраковки, решения, флаг частичных данных, независимость от `decimal.getcontext()`).

### Решения

- Наценка и порог карантина задаются в процентах (`20` = 20 %), коэффициент подозрительно низкой цены — долей (`0.5`). По умолчанию: порог 20 %, коэффициент 0,5, максимальный срок поставки 14 дней.
- Входные деньги не округляются и не обязаны иметь две цифры после запятой: округление — правило расчёта и применяется только по п. 7 (граница вверх, потолок вниз, целевая half-up). Поэтому цена конкурента вида `1250.005` даёт целевую `1240.01`.
- Порядок отбраковки предложения (первая сработавшая причина): другой артикул → другой бренд → цена ≤ 0 → нет в наличии (остаток ≤ 0) → срок поставки больше максимума → цена строго ниже закупка × коэффициент. Сравнение с коэффициентом идёт по точному произведению без округления.
- Приоритет причин «оставлена предыдущая»: некорректная закупка (≤ 0) → конфликт правил (потолок после округления строго меньше нижней границы после округления) → нет пригодных предложений. Промежуточные числа (граница, потолок, целевая) считаются и сохраняются и в этих случаях — для объяснения.
- Ограничения применяются к уже округлённой целевой цене: сначала нижняя граница, затем потолок; в `applied_constraints` попадает сработавшее.
- Решение о карантине: `abs(new − old) × 100 > порог × old` — то же, что `abs(new − old) / old × 100 > порог`, но без деления, то есть точно. Изменение ровно на пороге — не карантин. `change_percent` хранится точным (со знаком), `change_percent_display` — округлённым до 0,1 по ROUND_HALF_UP (−25,1 % для 1 990 → 1 490).
- Расчёт выполняется в собственном `decimal.Context` (28 знаков, ловушки на InvalidOperation/DivisionByZero/Overflow), результат не зависит от контекста вызывающего кода.
- Неверные входные данные конфигурации — `ValueError`/`TypeError` при создании dataclass-а: опубликованная цена ≤ 0, отрицательные наценка/шаг/порог/коэффициент, отрицательные остаток или срок, пустые после нормализации бренд или артикул товара. Нулевая или отрицательная закупка — не исключение, а результат «оставлена предыдущая».
- Нормализация: артикул — только буквы и цифры (`str.isalnum`) в верхнем регистре; бренд — trim, схлопывание пробелов, верхний регистр, затем таблица синонимов (Bosch, MANN-FILTER, Mercedes-Benz, MAHLE, Febi, Hengst, Valeo, Toyota, Volkswagen). Неизвестный бренд — очищенная форма в верхнем регистре.
- `RULES_VERSION = "2026-11-12.1"`; меняется при любом изменении правил.

CHECK: рекомендация пуста ровно у `retained`; причина пуста ровно у `published`/`unchanged`.

### Решения

- Долг шага 2 закрыт: цены предложений тоже `NUMERIC(12,2)`. Цена с источника с больше чем двумя знаками после запятой — ошибка структуры парсера (шаги 4–5).
- Порог подозрительно низкой цены (`закупка × коэффициент`) отдельным столбцом не хранится: он точно восстанавливается из снимка закупки и коэффициента и может иметь больше двух знаков. Коэффициент в конфигурации ограничен 4 знаками после запятой, чтобы снимок `NUMERIC(6,4)` хранил его без округления.
- Процент изменения — не деньги: `change_percent` хранится точным в `NUMERIC` без масштаба, `change_percent_display` — округлённым до 0,1.
- `finish_reason` — текст, а не enum PostgreSQL: коды причин завершения (кроме `interrupted`) определят шаги 5–6 без миграции.
- Частичный уникальный индекс построен на константе `(true)`, а не на `status`: так в queued/running может быть ровно одна строка суммарно, а не одна на каждый статус.
- Seed добавляет только отсутствующие товары (по нормализованной паре, `ON CONFLICT DO NOTHING`) и опубликованные цены только для только что добавленных; существующие строки, прогоны и опубликованные цены не трогает. Поэтому его безопасно запускать на каждом старте (entrypoint шага 4). Обновить настройки товаров из `seed_data.py` можно только через reset.
- Reset — `TRUNCATE` всех таблиц `RESTART IDENTITY CASCADE` и seed в одной транзакции: состояние совпадает со свежим seed, включая id. `published_at` у цен из seed фиксирован (`2026-11-01 09:00 UTC`), поэтому состояние детерминировано.
- Коды источников: `html_catalog`, `json_api`.

### Ручная проверка в compose

`docker compose up --build -d` поднял postgres, fake-sites, api (healthy после миграций и seed), worker. Затем `python -m app.db.reset` в контейнере api, `POST /api/runs` → `{"id":1,"status":"queued","created":true}` (201), повторный → `{"id":1,…,"created":false}` (200); через секунду `GET /api/runs/1` → `succeeded`, `html_catalog` ok, 26 предложений; `GET /api/published-prices` → `{"product_id":1,"brand":"Bosch","article":"0986452041",…,"price":"1240.00","calculation_id":1}`. Лог воркера: `run 1 finished: succeeded, 25 calculations, 12 published`. После проверки — reset и `docker compose down` (том оставлен).

### Решения

- Частичных результатов источника нет: ошибка на любом артикуле делает весь источник failed в этом прогоне, предложения источника не пишутся. Иначе товары, на которых источник упал, тихо считались бы без него, а флаг частичных данных стоял бы не там.
- Источник ищет по каждому различному нормализованному артикулу товаров один раз. Предложение пишется один раз; `offers.product_id` ставится только при точном совпадении нормализованной пары бренд+артикул (у `MANN 0986452041` — NULL). В расчёт товара идут все предложения прогона с его нормализованным артикулом: «другой бренд» отбрасывает и объясняет ядро.
- HTTP-статусы без повторов: таймаут, ошибка соединения или прокси и 5xx → network; 403 и 429 → blocked; прочие не-200 (404, редиректы — `follow_redirects=False`) → structure: площадка отвечает не так, как ожидает парсер. Ошибка декодирования ответа → structure. Посторонние исключения (ошибки кода) не маскируются под ошибку источника: воркер переводит прогон в failed с `finish_reason = internal_error`.
- Сообщения ошибок источников — на русском (их увидит менеджер), с артикулом, на котором произошёл сбой.
- Все источники упали → прогон failed, `finish_reason = all_sources_failed`; пишутся только `source_results`, расчётов и предложений нет, опубликованные цены не меняются.
- Транзакция 2 завершает прогон условием `status = 'running'`; если прогон уже не running (шаг 6: interrupted), публикация откатывается и бросается `RunNotRunningError`. Результаты транзакции 1 при этом остаются как история.
- `published_at` у опубликованной цены и `finished_at` прогона — `now()` транзакции 2, то есть совпадают.
- Деньги в API — `Decimal`, сериализуемый строкой (`"1240.00"`); значения из `NUMERIC(12,2)` всегда с двумя знаками.
- `POST /api/runs`: `ON CONFLICT DO NOTHING` без цели — у `runs` нет других уникальных ограничений, кроме ключа и `uq_runs_single_active`.

## Шаг 5. JSON-источник, режимы сбоев, повторы и бюджет времени

### Что сделано

  - `modes.py` — режимы `normal` / `markup_changed` / `unavailable` / `blocked` / `price_spike` в памяти экземпляра приложения, отдельно для `html_catalog` и `json_api`; управление `GET /control/modes`, `PUT /control/modes/{source}` (`{"mode": …, "retry_after": int?}`, `retry_after` по умолчанию 60, 0…3600), `POST /control/reset` (оба в normal). Режим действует на следующий запрос без перезапуска;
  - HTML: `markup_changed` — новая вёрстка карточками без `#offers` и без ячеек цены, остатка и срока; `unavailable` — 503; `blocked` — 403 со страницей капчи; `price_spike` — S стоит 1 500;

- backend:
  - `app/parsers/http.py` — `SourceHttp.get` с политикой повторов (`RetryPolicy`: 3 попытки всего, пауза 1 с, 2 повтора после 429), бюджетом источника (`Budget`) и внедряемыми часами (`Clock`: `monotonic()` и `sleep()`; `SYSTEM_CLOCK` в бою, `FakeClock` в тестах). Таймаут, ошибка соединения или прокси, 5xx → повторы с паузой, затем network; 403 → blocked сразу; 429 → пауза `Retry-After` (без заголовка — пауза политики), если она меньше остатка бюджета, иначе blocked сразу без ожидания; прочие ответы отдаются парсеру;

Исчерпание после сетевых сбоев → network, после 429 → blocked;
  - `app/parsers/json_api.py` — `JsonApiSource`: одна сессия на сбор (cookie jar `httpx.AsyncClient`), затем запросы прямо в API. 401 → одно переоткрытие сессии на весь сбор (под замком: параллельные 401 переоткрывают её один раз), повторный 401 → blocked «доступ отклонён». Нет cookie после витрины → structure. JSON разбирается с `parse_float=Decimal`, `NaN`/`Infinity` отвергаются; цена — только строка из цифр с не более чем двумя знаками после точки (`parse_api_price`), остаток и срок — целые JSON-числа (`parse_api_count`); число вместо строки, 3 знака, отсутствующее или переименованное поле, не JSON → structure, а не 0;
  - HTML-источник переведён на `SourceHttp` (те же повторы и бюджет);
  - настройки: `ENABLED_SOURCES` по умолчанию оба источника, `JSON_API_PROXY`, `SOURCE_RETRY_ATTEMPTS`, `SOURCE_RETRY_PAUSE_SECONDS`, `SOURCE_RATE_LIMIT_RETRIES`; `build_sources` даёт каждому источнику свой клиент, бюджет, семафор и таймауты; источники собираются параллельно (`collect_all`);

  - сообщения ошибок содержат код ответа, путь, артикул и число попыток, например «площадка недоступна: HTTP 503 на /html/search (артикул 0986452041), попыток: 3».

### Решения

- `unavailable` и `blocked` действуют на все страницы источника, включая витрину JSON, поэтому ошибки витрины проходят ту же политику повторов. `markup_changed` и `price_spike` меняют только данные.
- 429 на HTML-источнике (площадка его не отдаёт, но парсер к нему готов) обрабатывается так же, как на JSON.
- Пауза после 429 начинается, только если она строго меньше остатка бюджета: иначе после паузы не осталось бы времени на сам запрос.
- `Retry-After` в форме HTTP-даты не поддерживается и считается отсутствующим (пауза политики, затем лимит повторов 429 → blocked).
- Целое JSON-число в поле цены — тоже structure: контракт передаёт деньги строками, отклонение от контракта — смена схемы.
- 401 на витрине и прочие не-200 ответы API (404, 3xx) — structure. 401 в API — вопрос сессии (переоткрытие), повторный 401 — blocked.
- Сессия переоткрывается не больше одного раза за сбор источника, а не на каждый артикул: иначе 24 артикула давали бы до 24 переоткрытий.
- `FailingSource` в `tests/fakes.py` оставлен: им задаётся отказ второго источника в тесте записи прогона «оба источника упали», где важна запись, а не парсер. Тот же сценарий на настоящих парсерах — `test_unavailable_on_both_fails_the_run_and_changes_no_price`. `CatalogJsonSource` удалён.

### Отступления от plan.md

- Повторы реализованы явным циклом в `app/parsers/http.py`, а не через tenacity из раздела «Стек»: решение о повторе зависит от ответа (403 / 429 / 5xx), пауза — от `Retry-After` и остатка бюджета, а часы и `sleep` внедряются, чтобы тесты проверяли «без ожидания» и не спали. tenacity в зависимости не добавлен.

### Что сделано

- `app/db/runs.py`:
  - `recover_interrupted_runs` — одним `UPDATE … WHERE status = 'running' RETURNING id` переводит все прогоны в running в failed, `finish_reason = interrupted`, `finished_at = now()`; queued не трогает;

### Ручная проверка в compose

`docker compose up --build -d --wait`, `docker compose exec api python -m app.db.reset`, `POST /control/reset`, затем:

Прогон ждал `Retry-After 20` JSON-источника. На SIGTERM воркер решил выйти после итерации, но Docker убил его по истечении `StopTimeout` (в этом окружении у всех контейнеров 1 с, exit 137; при обычных 10 с исход тот же — пауза 20 с). То же через `docker compose stop worker` во время прогона 2; затем `POST /control/reset` и `docker compose start worker` → прогон 2 failed/`interrupted`, новый прогон 3 `succeeded` (html ok 26, json ok 24; `run_id=3 run finished: succeeded, 25 calculations, 11 published`), A = 1240.00 с `calculation_id` 1 (у прерванных прогонов расчётов нет), S = 1990.00.

Расписание отдельно: `SCHEDULE_INTERVAL_SECONDS=20 docker compose up -d worker` → `run_id=4 scheduled run queued … run finished: succeeded, 25 calculations, 0 published`, через 20 с то же для `run_id=5` (trigger `schedule`). После проверки — reset, `POST /control/reset`, `docker compose down`.

### Решения

- Восстановление — одна транзакция при старте воркера, до первой итерации. Расчёты и предложения прерванного прогона (если транзакция записи успела) остаются историей; публикация идёт только в транзакции завершения с условием `status = 'running'`, поэтому из прерванного прогона ничего не публикуется. Новый прогон считается с нуля.
- «Сейчас» для расписания — часы БД (`now()`), те же, что ставят `runs.created_at`. Тест передаёт `now`, и прогон по расписанию создаётся с этим `created_at`, чтобы часы были одни.
- «Последний прогон» — по `created_at` прогона с любым источником запуска и любым статусом (в том числе failed): иначе после серии сбоев расписание ставило бы прогон на каждой итерации.
- **В compose расписание по умолчанию выключено** (`SCHEDULE_INTERVAL_SECONDS` = 0), в приложении — 600, как решил прораб. Причина: при пустой таблице `runs` (первый `up` и каждый reset) правило «прогонов нет → пора» ставит прогон через ~2 с. Он публикует A = 1 240, и ручной шаг 2 сценария показывает «без изменений» вместо публикации — нарушается условие seed 1. План требует показывать расписание отдельно: `SCHEDULE_INTERVAL_SECONDS=60 docker compose up -d worker`. В `.env.example` переменная закомментирована, потому что compose читает `.env`. Прорабу: если расписание должно быть включено в поставляемой конфигурации, нужно другое правило для пустой БД (например, отсчёт от старта воркера), а это меняет решение «пустая БД → прогон».
- Пауза `WORKER_POLL_SECONDS` — после каждой итерации, в том числе после выполненного прогона: одновременно активен только один прогон, следующего в очереди всё равно нет.
- SIGTERM не прерывает текущий прогон: выход после итерации. Если Docker убивает процесс раньше (grace period), прогон восстанавливается при следующем старте. `stop_grace_period` не увеличен: иначе `docker compose restart worker` ждал бы окончания прогона.
- `restart: unless-stopped` у worker: упавший процесс поднимается сам и восстанавливает свой прогон.
- «Без изменений» и карантин `published_prices` не трогают — публикуются только расчёты `published` (решение шага 4, теперь закреплено тестами).
- `process_next_run` поднимает `RunCrashedError` вместо исходного исключения, чтобы цикл не печатал трассировку второй раз без run_id.
- Решение для шага 7: reset через API отвечает 409, если есть queued или running прогон. Здесь не реализуется; `python -m app.db.reset` остаётся без проверки.

### Что сделано

### Решения

- `latest_run`, `active_run` и `last_finished_run` отдаются все три: экрану нужно и «что идёт сейчас», и «чем кончился последний прогон». Источники — у каждого прогона свои; у queued/running и у прогона, прерванного до записи, список пуст.
- «Последний расчёт» товара — из новейшего прогона succeeded/partial (по `run_id`). Прогон failed расчётов не пишет; interrupted и internal_error могли успеть записать, но не опубликовали — показывать их как текущую рекомендацию было бы неправдой. Сами расчёты доступны по id (`run_status` в ответе).
- Для оставленной цены экран берёт причину из `latest_calculation`, а дату — из `published.calculated_at` (расчёт, по которому цена опубликована) или `origin = seed`.
- Подписи отдаёт сервер рядом с кодом (`state` + `state_label` и т. п.), чтобы у фронтенда не было своей таблицы подписей. Коды — enum в схеме, станут union-типами TS.
- Reset: сначала режимы, потом БД (замечание ревью: при обратном порядке прогон, поставленный между коммитом сброса БД и сбросом режимов, выполнялся со старыми режимами и оставался в БД после ответа 200). Транзакция во время HTTP не открыта, поэтому общей блокировки на всю операцию нет; вместо неё порядок: прогон, выполненный во время сброса режимов, стирается последующим TRUNCATE, а поставленный и не завершённый — даёт 409 на повторной проверке под `LOCK TABLE runs IN EXCLUSIVE MODE` (между этой проверкой и очисткой нельзя ни поставить, ни забрать прогон). Итог 200 означает: режимы normal и БД в состоянии seed на момент коммита. Оба случая покрыты тестами с подменённым транспортом fake-sites. CLI `python -m app.db.reset` остаётся без проверки (решение шага 6).
- `DemoMode` объявлен в backend (fake-sites — только dev-зависимость); тест сверяет его с `fake_sites.modes.Mode`.
- В каждой строке лога есть `service`, чтобы строки api и worker различались и при общем сборе. Вывод alembic и `seed` при старте api остаётся текстовым (одноразовый вывод до запуска сервиса).
