# Расчёт цены

Правила фиксированы (раздел «Правила расчёта» [plan.md](../plan.md#правила-расчёта)); редактора настроек нет. Код — чистая функция `calculate_price` в [backend/app/pricing/calculate.py](../backend/app/pricing/calculate.py), без БД, сети и времени. Как запустить демо — [README](../README.md); что делать при сбое источника — [runbook](runbook.md).

## Деньги

- Только `Decimal` в Python, `NUMERIC(12,2)` в БД, строки в JSON (`"1240.00"`). `float` ядро не принимает (`TypeError`), NaN и бесконечности — `ValueError`.
- Расчёт идёт в собственном `decimal.Context` (28 знаков, ловушки на `InvalidOperation`, `DivisionByZero`, `Overflow`), результат не зависит от контекста вызывающего кода.
- Входные деньги не округляются: округление — правило 7 и применяется только там. Цена предложения с больше чем двумя знаками после запятой до ядра не доходит — парсер считает её ошибкой структуры.
- Все цены — в рублях за штуку, на одной налоговой основе.

## Правила

**1. Пригодные предложения.** В расчёт товара идут только предложения текущего прогона с тем же нормализованным артикулом; предложения прошлых прогонов не используются. Каждое предложение проверяется по порядку, **первая сработавшая причина** и записывается:

| № | Условие | Причина (код) |
|---|---|---|
| 1 | нормализованный артикул другой | «другой артикул» (`other_article`) |
| 2 | нормализованный бренд другой | «другой бренд» (`other_brand`) |
| 3 | цена ≤ 0 | «цена не больше нуля» (`non_positive_price`) |
| 4 | остаток ≤ 0 | «нет в наличии» (`out_of_stock`) |
| 5 | срок поставки > максимального (14 дней) | «срок поставки больше допустимого» (`delivery_too_long`) |
| 6 | цена **строго** ниже закупка × коэффициент | «подозрительно низкая цена» (`suspiciously_low_price`) |

Нормализация: артикул — только буквы и цифры в верхнем регистре (`0 986-452 041` → `0986452041`, `OC 90` → `OC90`); бренд — обрезка и схлопывание пробелов, верхний регистр, затем таблица синонимов демо-набора (`MB` → Mercedes-Benz, `MANN` → MANN-FILTER, `KNECHT` → MAHLE и др., `backend/app/pricing/normalize.py`). Исходные значения хранятся рядом с нормализованными.

**2. Подозрительно низкая цена.** Порог = закупка × коэффициент (по умолчанию 0,5), сравнение по точному произведению без округления. Цена ровно на пороге не отбрасывается. Это защита от мусора вроде «1 250» → 1.

**3. Достаточно одного пригодного предложения.** Если один источник упал, расчёт по второму допускается, результат помечается «по частичным данным» (флаг `partial_data`). На сами числа флаг не влияет.

**4. Целевая цена** = минимальная пригодная цена конкурента − шаг.

**5. Нижняя граница** = закупка × (1 + наценка / 100). Это **наценка на закупку**, а не маржа от выручки. Цена ниже нижней границы не публикуется никогда.

**6. Потолок** (если задан) ограничивает результат сверху. Потолок ниже нижней границы — конфликт правил, новая цена не публикуется.

**7. Округление и ограничение** — строго в таком порядке:

1. нижняя граница округляется **вверх** до копейки — `ROUND_CEILING`;
2. потолок округляется **вниз** до копейки — `ROUND_FLOOR`;
3. конфликт правил проверяется после округления: потолок строго меньше границы — конфликт; равенство допустимо;
4. целевая цена округляется до копейки по `ROUND_HALF_UP`;
5. округлённая целевая ограничивается интервалом: сначала снизу границей, затем сверху потолком. Сработавшее ограничение записывается: «ограничено снизу» (`lower_bound`) или «ограничено сверху» (`ceiling`).

**8. Карантин.** Изменение = abs(new − old) / old × 100, где old — опубликованная цена на момент расчёта.

- Рекомендация равна опубликованной → «без изменений».
- Изменение **строго больше** порога → «карантин» (`price_spike`). Сравнение точное и без деления: `abs(new − old) × 100 > порог × old`. **Изменение ровно на пороге — не карантин** (1 000 → 1 200 при пороге 20 % публикуется, 999,99 → 1 200 — карантин).
- Опубликованной цены нет → первая рекомендация тоже уходит в «карантин» (`no_previous_price`).
- Иначе → «опубликована».

Изменение хранится точным и со знаком (`change_percent`), для показа — округлённым до 0,1 по `ROUND_HALF_UP` (`change_percent_display`, −25,1 %).

**9. Новая цена не публикуется**, предыдущая остаётся, экран показывает причину и дату расчёта, по которому опубликована действующая цена (или «цена из исходных данных»). Если причин несколько, записывается первая по приоритету:

1. некорректная закупка — закупка ≤ 0 (`invalid_purchase_price`);
2. конфликт правил — потолок ниже нижней границы (`rules_conflict`);
3. нет пригодных предложений (`no_eligible_offers`).

Промежуточные числа (граница, потолок, целевая) считаются и сохраняются и в этих случаях — для объяснения.

## Состояния результата

| Состояние | Код | Рекомендация | Что с опубликованной ценой |
|---|---|---|---|
| опубликована | `published` | есть | заменяется рекомендацией при завершении прогона |
| без изменений | `unchanged` | равна опубликованной | не трогается |
| карантин | `quarantine` (`price_spike` / `no_previous_price`) | есть, видна на экране | не трогается; рекомендация в `GET /api/published-prices` не попадает, пока менеджер её не [подтвердит](#подтверждение-карантина) |
| оставлена предыдущая | `retained` (`invalid_purchase_price` / `rules_conflict` / `no_eligible_offers`) | нет | не трогается |

В `published_prices` пишут только расчёт `published` — в короткой транзакции завершения прогона — и подтверждение рекомендации из карантина; оба через `INSERT … ON CONFLICT (product_id) DO UPDATE`, со ссылкой на расчёт. Если прогон к этому моменту уже не running (прерван), ничего не публикуется. Прогон failed (оба источника упали) расчётов не пишет вовсе.

## Подтверждение карантина

[Расширение 1](../plan.md#расширения--по-порядку). Рекомендация из карантина сама не публикуется; если рынок действительно сдвинулся, менеджер подтверждает её кнопкой «Подтвердить» (`POST /api/calculations/{id}/confirm`), и она публикуется. Без подтверждения следующие прогоны снова дают карантин, пока изменение больше порога; первая рекомендация товара без опубликованной цены публикуется только подтверждением.

Подтвердить можно, только если рекомендация всё ещё последнее слово и её вход не изменился. Условия проверяются по порядку; первое нарушенное даёт код отказа (HTTP 409) и причину «… требуется новый расчёт» — нужен новый прогон:

1. состояние расчёта — «карантин» (`not_quarantine`);
2. расчёт ещё не подтверждён (`already_confirmed`): повторное подтверждение ничего не публикует второй раз;
3. расчёт из **последнего завершённого прогона** — последнего в статусе `succeeded` или `partial` (`superseded`): более новый прогон отменяет старые рекомендации. Прогон `failed` расчётов не даёт и ничего не отменяет; прогон в очереди или выполняемый подтверждению не мешает;
4. возраст расчёта `now − calculated_at` по часам БД не больше `QUARANTINE_CONFIRM_MAX_AGE_MINUTES` (по умолчанию 60 минут; ровно 60 — ещё можно) (`too_old`);
5. закупка товара равна закупке в снимке расчёта (`purchase_changed`);
6. версия правил расчёта равна текущей `RULES_VERSION` (`rules_changed`);
7. наценка, шаг, потолок и порог карантина товара равны снимку (`settings_changed`) — сверх `plan.md`: с другими настройками рекомендация была бы другой;
8. опубликованная цена сейчас равна `previous_price` снимка — той, с которой расчёт сравнивал (`published_changed`); для товара без опубликованной цены — её всё ещё нет.

Проверки и запись — одна транзакция. Она начинается с advisory-блокировки публикации (`pg_advisory_xact_lock`), которую берёт и транзакция завершения прогона, поэтому они выполняются строго по очереди: подтверждение, ожидавшее завершающийся прогон, видит его и получает `superseded`, а прогон, завершающийся после подтверждения, повторяет расчёт товаров, чья опубликованная цена изменилась после чтения, — с теми же предложениями против новой опубликованной цены (например, S после подтверждения 1 490 при конкуренте снова 2 000 даст карантин +33,6 %, а не перезапишет цену). Блокировка строк здесь не подходит: прогон, отменяющий рекомендацию, может вовсе не писать строку этого товара в `published_prices`.

При успехе в той же транзакции: `calculations.confirmed_at` = момент подтверждения, в `published_prices` — рекомендация с этим же `published_at` и `calculation_id` подтверждённого расчёта. Состояние расчёта остаётся «карантин» с отметкой «подтверждена»; у опубликованной цены источник — «подтверждена из карантина». Кто подтвердил, не хранится (авторизации нет). Экран получает из `/api/products` и `/api/calculations/{id}` признак `can_confirm` и код с причиной, почему нельзя, — кнопка неактивна с подсказкой; сервер всё равно проверяет условия заново.

## Что сохраняется в расчёте

Таблица `calculations`, одна строка на (прогон, товар) — уникальное ограничение:

- снимок входа: закупка, наценка %, шаг, потолок, порог карантина %, коэффициент подозрительно низкой цены, максимальный срок поставки, опубликованная цена на момент расчёта (`previous_price`), **версия правил**, флаг частичных данных;
- учтённые и отброшенные предложения (JSONB, деньги строками; у отброшенных — причина) с исходными и нормализованными брендом и артикулом, ценой, остатком, сроком, источником;
- минимальная цена конкурента, целевая до и после округления, нижняя граница, потолок после округления, сработавшие ограничения;
- рекомендация, состояние, причина, изменение (точное и для показа), время расчёта.

Из этого снимка `GET /api/calculations/{id}` и раскрытие «Почему цена такая» строят формулу с подставленными числами ([backend/app/pricing/explain.py](../backend/app/pricing/explain.py)).

## Настройки

| Настройка | Где задаётся | По умолчанию |
|---|---|---|
| минимальная наценка, % | товар (`products`, из `backend/app/db/seed_data.py`) | 20 |
| шаг ниже конкурента, ₽ | товар | 10 (у части товаров 5) |
| потолок, ₽ | товар | не задан (у MAHLE OC90 — 600) |
| порог карантина, % | товар | 20 (у Valeo 826704 — 15) |
| коэффициент подозрительно низкой цены | переменная `SUSPICIOUS_PRICE_FACTOR` | 0,5 |
| максимальный срок поставки, дней | переменная `MAX_DELIVERY_DAYS` | 14 |
| сколько минут после расчёта можно подтвердить карантин | переменная `QUARANTINE_CONFIRM_MAX_AGE_MINUTES` (сервис api) | 60 |

Наценка и порог задаются в процентах (`20` = 20 %), коэффициент — долей (`0.5`). Настройки товара меняются правкой `seed_data.py` и сбросом (`python -m app.db.reset`): seed не обновляет уже существующие товары.

**Версия правил** — `RULES_VERSION` в [backend/app/pricing/models.py](../backend/app/pricing/models.py), сейчас `2026-11-12.1`. Меняется при любом изменении правил и сохраняется в каждом расчёте; видна в раскрытии «Почему цена такая».

## Разобранные примеры

Все — закупка 1 000 ₽, наценка 20 %, шаг 10 ₽, без потолка, порог 20 %, коэффициент 0,5.

**A, конкурент 1 250 ₽ → 1 240 ₽** (шаг 2 сценария; опубликовано 1 260 ₽):

```
Нижняя граница = 1 000,00 × (1 + 20 %) = 1 200,00 (округление вверх до копейки)
Порог подозрительно низкой цены = 1 000,00 × 0,5 = 500,00: предложения дешевле отбрасываются
  MANN 0986452041, 1 150,00 → MANN-FILTER ≠ Bosch → «другой бренд»
  Bosch 0 986 452 041, 1,00 → 1,00 < 500,00 → «подозрительно низкая цена»
Минимальная цена конкурента = 1 250,00 (пригодных предложений: 2)
Целевая = 1 250,00 − 10,00 = 1 240,00
Итог 1 240,00: ограничений нет
Изменение = |1 240,00 − 1 260,00| / 1 260,00 × 100 = 1,6 % ≤ 20 % → опубликована
```

**Конкурент 1 100 ₽ → 1 200 ₽** (ограничено снизу): целевая 1 100 − 10 = 1 090,00 ниже нижней границы 1 200,00 → итог 1 200,00, «ограничено снизу». Цена ниже границы не публикуется никогда.

**S, `price_spike`: конкурент 1 500 ₽ → 1 490 ₽, −25,1 % → карантин** (шаг 5 сценария; опубликовано 1 990 ₽):

```
Нижняя граница = 1 200,00; порог подозрительно низкой цены = 500,00
Минимальная цена конкурента = 1 500,00 (JSON API; HTML-каталог даёт 2 100,00)
Целевая = 1 500,00 − 10,00 = 1 490,00
Итог 1 490,00: ограничений нет
Изменение = |1 490,00 − 1 990,00| / 1 990,00 × 100 = 25,1256… % > 20 % → карантин
```

Опубликованная цена S остаётся 1 990,00 ₽. Числа подобраны так, что результат не упирается в нижнюю границу (1 490 > 1 200) и предложение не попадает под фильтр подозрительно низкой цены (1 500 > 500).

**Округление** (строки `control_cases.csv`):

| Строка | Вход | Результат |
|---|---|---|
| `markup_fractional_ceil` | закупка 100,01, наценка 13 %: 100,01 × 1,13 = 113,0113 | граница вверх → 113,02 |
| `target_half_cent_up` | конкурент 1 250,005: 1 250,005 − 10 = 1 240,005 | целевая half-up → 1 240,01 |
| `target_below_half_cent` | конкурент 1 250,004: 1 240,004 | → 1 240,00 |
| `ceiling_floor_rounding` | потолок 1 300,019 | потолок вниз → 1 300,01 |
| `ceiling_below_lower_bound` | потолок 1 199,99 < граница 1 200,00 | конфликт правил, «оставлена предыдущая» |
| `ceiling_equals_lower_bound` | потолок 1 200,00 = граница | допустимо → 1 200,00 |
| `threshold_exact_up` / `threshold_just_over` | 1 000 → 1 200 (ровно +20 %) / 999,99 → 1 200 (+20,0012 %) | опубликована / карантин |

## Сверка: `control_cases.csv`

Файл [backend/tests/data/control_cases.csv](../backend/tests/data/control_cases.csv) — 25 вручную рассчитанных примеров: в каждой строке входные данные расчёта (бренд, артикул, закупка, наценка, шаг, потолок, опубликованная цена, порог, предложения) и ожидаемый результат (цена, состояние, причина, причины отброшенных предложений). Ожидаемые значения не генерируются кодом. Формат колонок — [backend/tests/data/README.md](../backend/tests/data/README.md). Это контрольные примеры, а не доказательство совместимости со старой системой; команда сверки с выгрузкой старой системы — расширение 3.

Запуск:

```sh
uv run --directory backend pytest tests/unit/pricing/test_control_cases.py
```

Последняя строка перед итогом pytest — `control cases: N matched, M mismatched` (сейчас `control cases: 25 matched, 0 mismatched`). Строка печатается и в полном прогоне `pytest`. При расхождении тест показывает входные данные строки, ожидаемое, фактическое и промежуточные числа. Шаг 7 скрипта `scripts/demo_scenario.py` запускает тот же тест и проверяет `0 mismatched`.
